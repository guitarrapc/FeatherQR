## 総括者が自分でコードを読んで裏付けた所見

- F1 (拡大): `IconArea.cs:60` のガードはファインダー重なりしか防がない。v1・アイコン 7・ボーダー 0 (start=7, 行列 7-13) は通り、形式情報第 1 コピーの (7,8)(8,7)(8,8) に加え、第 2 コピーの (8,13) とダークモジュール (13,8) も明色に塗る。
- B6: `MicroQRCodeDecoder.cs:445` のコメントは誤り。コアは奇数サイズでタイミングは偶数座標が暗いので、コアの右上と左下の角は常に暗く、bounding box でコアを測れる。非対称の静寂域を拒否する挙動 (`top != left`) を rMQR に揃えるかは要判断。
- D9: `EccBinaryDecoder.cs:143` は到達不能。Λ (λ0=1、次数 L 以下) が異なる L+1 点で 0 になることはない。L 個見つけた時点で break できる。
- I-1: `RmQRFormatInformationDecoder.TryDecode` は 64 語×2 の PopCount を総当たりしている。片側の語間距離が 7 以上なら、期待版の 2 語との比較 (4 回) で同じ判定になる。
- E1: `FinderPatternFinder.Simd.cs:22-27`。行幅 4096 px 以上は edge-list の上限 (`EdgeListWidthLimit = 4096`) を超えてマスクウォークに来る。その幅では必ず `maskLength > 64` なので、毎行 ArrayPool から借りて返す。
- C1: `TextAnalyzer.X86.cs:29-34` は `Vector256.Create(text[i], ... text[i+15])` で 16 要素を個別に挿入している。Vector128 と Arm64 は `LoadUnsafe` 1 回。
- C4 / G01: `Polynom` / `PolynomItem`、`QRCodeConstants` の `capacityTable` / `CapacityTable` / `CapacityECCTable` / `VersionInfo*` は src にも tests にも参照がない。
- H-1: `QRImageDecoder.cs:1157-1158` の手書きクランプは NaN を素通しする。netstandard2.0 ビルドを .NET Framework や .NET 8 以前で動かすと `(int)NaN = int.MinValue` で範囲外になる。到達経路は未確認。Micro QR の `IsDarkAt` も同型 (D23)。
- H-2: SkipLocalsInit は使っていない (spec の決定)。そのため `DecodeThroughTimingFrame` は早期 return の前に 1,424 B の stackalloc をゼロ埋めしている。判定を stackalloc より前に移すだけで済む。
- A6 / G18 / H-10: `[ThreadStatic]` のテスト用カウンタ (`QRCodeGenerator.ChunkPlans...` 等、`StructuredAppendPlanner.ScalarWalks/LaneBatches`、`QRImageDecoder.ModuleBuffersOut/Peak`) を本番経路でインクリメントしている。doc に「テストのため」と明記された意図的なもの。挙動を切り替えるスイッチではないので「src にテスト専用スイッチを置かない」規則の文言には当たらない。ただし趣旨には触れるので、残すかは要判断。

## 優先度順のおすすめ

### 1. 正しさ・仕様判断 (先に決める)
1. F1 アイコン領域が形式情報とダークモジュールを塗る問題 (`IconArea.cs:60`): 下限を 9、上限を core-9 にするか、spec で許容を明記する。
2. B6 Micro QR の非対称の静寂域 (`MicroQRCodeDecoder.cs:443-490`): rMQR と同じく受理するか、拒否を維持してコメントだけ直すか。
3. H-1 / D23 / I-16 / E14 / E9 サンプラーのクランプの不統一: 手書きクランプと `(int)` 切り捨てを `PixelIndex.Clamp` / `VectorCast.ToPixel` に揃える。NaN と ±Inf、負の小数が対象。
4. J2 `SKSurface.Create` の null 未検査 (`SymbolImageBuilderBase.cs:702`)、J1 FillCanvas の doc とコア側の挙動差、G10 (Gs1) の int 桁あふれ。
5. A1 / A2 / B2: 収まらないときの例外型 (QR だけ `InvalidOperationException`)、ParamName、寸法 0 以下のメッセージ。2.0.0 の freeze (Phase 7) で揃える候補。A15 `QRCodeData.IsFinderPattern/GetFinderPatternIndex` の公開も freeze 前に見直す。

### 2. 低リスクな無駄の削除 (読んで確認済み)
- 未使用コード: `Polynom.cs` (C4)、`QRCodeConstants` の capacity 表群 (G01)、`RmQRSegmentPlanner.ByteUnitCount` と短い `SelectVersion*` overload (I-10)、`ECCInfo.Version/ErrorCorrectionLevel` (C7)、`Vector2Slim` の未使用メンバ (J3)、`CharacterSets.IsValidISO88591(string)` (C6)。spec `qrcode-symbologies.md:29` の Polynom 記述も一緒に消す。
- 到達しない分岐・冗長な検査: D9 (Chien search)、D11 (SegmentDecoders の群ごとのビット検査)、B13 (Rgb24 X86 の末尾ループ)、E5 (`Math.Min` が常に同じ値)、H-19、C12 (FNC1 Latin ループの BOM 比較)。
- 同一コードの重複: `Widen` 3 箇所 (A9)、Micro QR 形式語 3 重定義 (D16)、MicroQR/rMQR の数字 SWAR と英数字表 (D20)、ECI ブロック (H-21)、`ThrowIfLuminanceDoesNotFit` 7 箇所 (B1)、Micro Optimal 経路 3 重 (A10)、Lanes Simd/Arm64 の 320 行 (G19)、SymbolRenderer の 3 overload (J4)。
- net10.0 だけになった後に残った `#if NET5/NET8/NET10` の入れ子と、古い "net8.0+" の doc (D2, C14)。

### 3. 計測して判断する性能候補 (効果が大きそうな順)
1. C1 TextAnalyzer の AVX2/SSE2 tier を `LoadUnsafe` に置き換える (x64 の主経路)。
2. I-1 rMQR の形式情報デコードを 128 回から 4 回の PopCount に減らす (grid 試行ごと、候補 1 つあたり最大 256 回)。
3. F8 StyledRaster の `ComposeRow` で、モジュール行ごとの計算を画素行ごとにやり直している。
4. E2 Micro/rMQR の 1 シンボル失敗時に strided 行を 2 回走査している。既存の replay 機構を使う。
5. B14 AVX2 の straight alpha で、部分 alpha が 1 画素あると行の残りが scalar になる。NEON と 128-bit tier にはベクトル版がある。
6. G10 `MaskCode64Vector128` が毎回 2.5 KB をゼロ埋めしている。AVX2 tier は 32 行と 64 行に分けている。ARM64 と Wasm の v1-3 で計測する。
7. D1 ARM64/Wasm にも RS の 2 ブロック同時カーネルを用意する。
8. I-9 `PlanFitsFnc1` に、`PlanFits` にある skip を入れる。
9. H-2 / H-3 stackalloc のゼロ埋めを早期 return の後ろに移す (読むだけで効果が明らか、コストもほぼ 0)。
10. E1 幅 4096 px 以上の行で、マスクを検索 1 回につき 1 回だけ借りる。
11. G06 `PlaceFormat` の stackalloc 初期化子を静的表 `FormatXs1/FormatYs1` に置き換える (Debug ビルドで割り当てが出る。G03 の整数化と合わせて)。

### 4. 判断が要る項目
- 本番経路のテスト用カウンタ (A6, G18, H-10) と、テストからしか使われない入口 (A5, A16, B10, C5, C6, E7, F12, G11, I-3, I-13): 残すか、internal のテスト用 helper に寄せるか。

## パリティ確認 (所見ではなく、確認した事実)

- 係数: scalar 77/150/29 (>>8)。AVX2 は [77, 51, 99, 29] の pmaddubsw のあと pmaddwd(1)。NEON は UDOT [77,150,29,0] (BGRA は [29,150,77,0])。128-bit は [c0,c2]·[77,29] (BGRA は入れ替え) + 150g。Rgb24 の各 tier は同じ重みを使い、filler byte には 0 を掛けるか mask で消している。いずれも合計 256 で、和は 65,280 以下。
- straight の合成: AVX2 と scalar は (c·a + 255·(255−a))/255。NEON と 128-bit は 255 − ceil((255−c)·a/255) を (t+1+(t>>8))>>8 で計算する。等価性は各ファイルのコメントの通りで、a=0 の whiten (0xFFFFFFFF → 255) も一致する。
- premultiplied で c > a の不正入力: scalar の `(byte)` cast による wrap を、AVX2 は `& 0xFF`、128-bit は `wrap` mask、NEON は narrowing の切り捨てで再現しており、一致する。
- tail: AVX2 4 バイトは 32 → 8 → 重ね合わせ 8 → scalar (幅 8 未満)。NEON / 128-bit は 16 ブロック + 重ね合わせ 16 で、幅 16 未満は dispatch が scalar に回す (`IsVectorTierTaken`)。Rgb24 の AVX2 は幅 8 以上、NEON / 128-bit は幅 16 以上。どの load も行の最終バイトを越えない (Rgb24 の LoadOctet24 と back テーブルも確認した)。
- ValidateExtents の必要長 `(h−1)·rowBytes + w·bpp` は、全 tier の最大読み取り位置と一致する。
